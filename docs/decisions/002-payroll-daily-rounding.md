# 002 — Посуточное округление в детальном payroll-отчёте

Статус: **superseded** решением ADR-005 (`docs/decisions/005-earnings-calculation.md` в
корне-оркестраторе, фича `shift_history_earnings`, 2026-09-01). ADR-005 вводит единый атом
округления — **смена** — для всех режимов (`granularity=none`, `day|week|month`, экспорт).
«Решение» ниже (посуточный атом в детальном режиме, единичное round-once для `none`) более
не действует; оставлено как исторический контекст. Актуальное правило и его обоснование —
в ADR-005 п.5.

Фаза: payroll_detailed_report
Влияет на: payroll (`granularity=none`), admin (сводки/матрица), любые будущие отчёты по деньгам

## Контекст

Базовый `GET /organizations/{id}/payroll` округляет начисление сотрудника half-up
**ровно один раз** на полную сумму за период (точное накопление `Decimal` → одна
квантизация до копейки). Это даёт минимальную ошибку округления на сотрудника.

Фича `payroll_detailed_report` вводит суточную разбивку (`breakdown[]`) и экспорт в
Excel, где деньги показываются по дням/неделям/месяцам. Если итог сотрудника
округлять один раз, а корзины — отдельно, суммы по корзинам в общем случае **не
сойдутся** в итог сотрудника (и в `totals`): таблица «не бьётся» по строкам, что
недопустимо в бухгалтерском отчёте, который выгружают в Excel и суммируют.

ТЗ (`docs/tasks/payroll_detailed_report/backend.md`) разрешило выбор: либо сделать
посуточное округление единым правилом и для `granularity=none`, либо сохранить старое
правило для `none` ради неизменности существующего контракта — с фиксацией в ADR.

## Решение

**Атомарная единица округления в детальном режиме (`granularity != none`) и в
экспорте — календарный день в таймзоне `tz`.** По каждому локальному дню сумма по
сменам считается точным `Decimal` и округляется half-up до копейки один раз. Корзины
`week`/`month`, итог сотрудника (`items[].gross_amount_minor`) и `totals` — это **суммы
уже округлённых дневных значений** (день → корзина → сотрудник → всего). Тогда любая
таблица сходится на всех уровнях.

**Режим `granularity=none` сохраняет прежнее правило** — единичное округление на итог
сотрудника. Причина: приёмка требует, чтобы `GET …/payroll` без новых query-параметров
возвращал **байт-в-байт** прежний контракт (обратная совместимость со старыми
мобильными билдами). Глобальный переход на посуточное округление сломал бы это (и
существующий тест `test_rounding_half_up_once_on_employee_total`).

Технически: посуточное округление переиспользует ту же функцию `_calc_earnings`
(округляет один раз на переданный набор смен) — она применяется к сменам **одного дня**;
`none`-режим применяет её ко **всем** сменам сотрудника сразу.

## Последствия

- `items[].gross_amount_minor` для одного и того же периода может отличаться между
  `granularity=none` и `granularity=day|week|month` на **≤ несколько копеек на
  сотрудника** (накопленная разница дневных округлений). Это ожидаемо и
  задокументировано; клиенты не должны считать два режима тождественными до копейки.
- Внутри детального режима суммы всегда консистентны: `Σ breakdown = item`,
  `Σ items = totals`. Excel-выгрузка суммируется без визуальных расхождений.
- Нарезка по дням зависит от `tz`: смена у границы суток попадает в день по локальному
  времени, поэтому при разных `tz` дневные суммы (а значит и округления) могут
  отличаться — это корректное следствие, а не баг.
- Если в будущем потребуется единое правило округления для всех режимов — менять только
  `none`-ветку (перейти на посуточную агрегацию), пересмотрев обратную совместимость
  контракта и затронутые тесты.
