> **Файловое хранилище (file_storage).** Единый слой хранения поверх S3-совместимого storage (локально MinIO, в проде managed S3 — переезд = смена `S3_*` env, без правок кода). Загрузка идёт **через бэкенд** (multipart → API → storage), доступ к объектам **приватный** — клиент качает по **presigned GET URL** с коротким TTL (`S3_PRESIGN_EXPIRE_SECONDS`), который генерирует бэк. `files` — чистый реестр блобов (`File`); привязка к бизнес-сущности делается со стороны фичи-потребителя FK на `files.id` (НЕ полиморфизм) — целостность и `ON DELETE` каскады. Категория (`FileCategory`) задаёт префикс ключа, политику (лимит размера + разрешённые MIME, таблица `CATEGORY_POLICIES` в `services/file_storage.py`) и права: `checklist_photo` — любой member org; `knowledge_base` — admin/owner org; `avatar`/`other` — персональные. Реальный MIME определяется по сигнатуре содержимого (`filetype`), а не по заголовку multipart; имя в ключе — всегда UUID (anti path-traversal/коллизии), исходное имя хранится для `Content-Disposition`. **presigned + MinIO:** бэк ходит в storage по внутреннему `S3_ENDPOINT_URL`, но presigned-ссылка генерируется клиентом на публичном `S3_PUBLIC_ENDPOINT_URL` (подпись сразу от публичного хоста; в managed-S3 оба совпадают). Прямой стрим байтов через бэк не делаем. Жизненный цикл: строка создаётся с `is_attached=false`, потребитель ставит `true` при привязке; сироты (`is_attached=false`, старше `ORPHAN_FILE_TTL_HOURS`) подбирает Celery `cleanup_orphan_files`. Ошибки — `FileError` (`FILE_NOT_FOUND`/`FILE_TOO_LARGE`/`UNSUPPORTED_FILE_TYPE`/`INVALID_FILE_CATEGORY`/`FILE_IN_USE`/`STORAGE_UNAVAILABLE`).

> **Фото-подтверждения чек-листов (checklist_photos).** Пункт шаблона несёт `photo_requirement` (none/optional/required) и `photo_source` (camera/camera_or_gallery — подсказка UI, сервер источник **не** enforce-ит); при `requirement=none` source нормализуется к camera. На старте org-смены настройки копируются снимком в `checklist_instance_items` (правка шаблона на уже созданные экземпляры не влияет). Загрузка файла — через существующий `POST /api/v1/files` (категория `checklist_photo`); фича только **привязывает** загруженный `file_id` к пункту-экземпляру (`checklist_item_photos`, UNIQUE на `file_id`). Привязка/отвязка — только владелец активной смены, под `SELECT ... FOR UPDATE` на пункт (защита лимита `CHECKLIST_MAX_PHOTOS_PER_ITEM`); проблема с файлом-кандидатом (нет/чужой/другая org/не `checklist_photo`/уже привязан) → единый `PHOTO_FILE_INVALID`. Привязка ставит `files.is_attached=true`; отвязка снимает флаг и зовёт `delete_file` (объект S3 + строка `files`, связь уходит каскадом). Статус экземпляра считает **единая** функция `_recompute_instance_status` по критерию **satisfied** = `is_completed AND (photo_requirement != required OR photos_count >= 1)`; вызывается из PATCH пункта и привязки/отвязки фото, поэтому `finalize_shift_checklists` (и его sync-двойник) по-прежнему доверяют хранимому статусу. Режим **мягкий**: отметить пункт без фото и завершить смену можно — отсутствие обязательного фото лишь даёт `pending`→`incomplete` и `has_incomplete_required_checklists`. Деталь экземпляра отдаёт по каждому фото свежий presigned GET (батч-подпись одним клиентом, без N+1); при недоступности storage — `url=null` без 502 (клиент дотянет через `GET /files/{id}`). `items_summary` списка получил `satisfied_count` (честный прогресс) и `photos_required_missing` (бейдж «нужно фото») — одним GROUP BY. **Privacy-долг:** `cleanup_shift_photo_files` (в `services/checklist_instance.py`) удаляет файлы привязанных фото смены ДО каскадного сноса связей, НО прямого триггера нет — смены не hard-удаляются, org — soft-delete; `cleanup_orphan_files` не подбирает `is_attached=true`, поэтому при будущем hard-delete смены/org гео-привязанные фото останутся объектами S3 (массовая чистка бакета — отдельная DevOps-задача).

> **База знаний (knowledge_base).** Дерево разделов/страниц org с бесконечной вложенностью (`knowledge_nodes`, self-ref `parent_id`); контент страницы — массив блоков в JSONB (BLOCK SCHEMA `schema_version=1`: heading/paragraph/bulleted_list/numbered_list/quote/callout/divider/image/file/video(youtube)/table; `span` = inline rich-text). Только организационный режим. **ACL** (`knowledge_node_access`): правило `allow`/`deny` на роль или конкретного member; эффективный доступ employee к узлу считается обходом вверх по `parent_id` с приоритетом категорий — (1) персональное правило (member_user_id), (2) ролевое (role_id кастомной роли), (3) `all_members` на узле/предке, (4) deny по умолчанию; персональное всегда сильнее ролевого, внутри категории ближайший узел перебивает дальний (`services/knowledge._resolve_employee`, индекс ACL грузится одним проходом — без N+1). owner/admin/super_admin игнорируют ACL (полный доступ). Employee без эффективного allow видит узел как несуществующий (`404 KNOWLEDGE_NODE_NOT_FOUND`, не 403); дерево для employee отдаёт доступные узлы + разделы-предки как навигационные контейнеры (поле `all_members` опускается). **Файлы** грузятся через `POST /api/v1/files` (категория `knowledge_base`, admin/owner, 50 MB, image/*+pdf+OOXML docx/xlsx/pptx; OOXML — только без макросов: `vbaProject.bin`/`macroEnabled` в контейнере или битый архив → 415 `UNSUPPORTED_FILE_TYPE`; generic zip и легаси doc/xls/ppt запрещены) и привязываются к странице **через её `content`** (блоки image/file): на PATCH сервер диффит множества `file_id` в одной транзакции — новые валидирует (`knowledge_base`, та же org, не привязан к другой странице → иначе `400 KNOWLEDGE_FILE_INVALID`) и ставит `is_attached=true` + строку `knowledge_node_files` (`UNIQUE(file_id)` — один файл = одна страница, гонка двух страниц ловится конфликтом UNIQUE), исчезнувшие — `is_attached=false` + `delete_file` (объект S3 + строка `files`); добавления идут до удалений (необратимый S3-delete не теряется при откате). На чтении страницы блоки image/file обогащаются свежим presigned `url`/`url_expires_at` (батч-подпись, при сбое storage — `url=null` без 502; в хранимом `content` только `file_id`). Перемещение (`parent_id`) проверяет цикл подъёмом по предкам (`400 KNOWLEDGE_NODE_CYCLE`), чужой parent → `404`. **Privacy-критично:** `delete_node` (M5) собирает `file_id` всего поддерева и удаляет объекты S3 + строки `files` ДО каскадного `ON DELETE CASCADE` (иначе `cleanup_orphan_files` их не подберёт — они `is_attached=true`); при hard-delete org объекты S3 останутся — массовая чистка бакета вынесена в **общий DevOps-долг с `checklist_photos`**. Ошибки — `KnowledgeError` (`KNOWLEDGE_NODE_NOT_FOUND`/`KNOWLEDGE_NODE_CYCLE`/`KNOWLEDGE_FILE_INVALID`) + переиспользуемые `FORBIDDEN`/`ROLE_NOT_FOUND`/`MEMBER_NOT_FOUND`/`VALIDATION_ERROR`/`ORG_NOT_FOUND`.

Деталь чужой org-смены строго проверяет `shift.organization_id == org_id` → иначе `404 SHIFT_NOT_FOUND` (персональные/чужие смены не раскрываются). > **Привязка точки к смене (`shift_work_location`).** При старте орг-смены фиксируется `shifts.work_location_id` по матрице двух настроек org (`geo_check_enabled` × `require_work_location`): **гео вкл** — точку определяет сервер (ближайшая по Haversine из зон, в радиус которых попал сотрудник; присланный клиентом `work_location_id` игнорируется; вне зон — прежний `403 GEO_CHECK_FAILED`); **гео выкл + require** — клиент обязан прислать `work_location_id` (нет → `422 WORK_LOCATION_REQUIRED`); **гео выкл + не require** — точка опциональна. Любой переданный id, не принадлежащий org (или с невалидным форматом), → `404 WORK_LOCATION_NOT_FOUND`. Точка ставится один раз на старте (паузы/возобновления её не меняют); логика — `services/shift._resolve_org_shift_start`. Персональные смены (`org_id=null`) точку не привязывают. `ShiftResponse` отдаёт additive nullable `work_location_id` + денормализованный `work_location {id, name, address}` (текущее значение точки, eager `selectinload(Shift.work_location)` во всех читающих смену запросах). Настройку `require_work_location` нельзя включить без точек (`409 WORK_LOCATION_REQUIRED_NO_LOCATIONS`); удаление последней точки гасит и `geo_check_enabled`, и `require_work_location` (симметрично). Помимо `OrganizationSettings*` (RBAC owner/admin) обе настройки `geo_check_enabled` и `require_work_location` **флэттятся в `OrganizationResponse` и `JoinResponse`** (`_org_to_response` / join, из `org.settings.* if org.settings else False`) — чтобы employee (без доступа к `/settings`) активировал обязательный выбор точки на клиенте. Разблокирует фильтр по точке в `payroll_detailed_report`.

> существует). `GET .../members/{id}/checklists` получил additive `location_ids`
> на каждом элементе и опциональный query `work_location_id`: без параметра —
> весь `by_assignment` набор без фильтра (обратная совместимость), с параметром —
> ровно то, что сотрудник получил бы, открыв смену на этой точке (валидация
> принадлежности точки org → `404 WORK_LOCATION_NOT_FOUND`). Удаление точки
> каскадно снимает привязки; шаблон, оставшийся без привязок, снова действует
> везде (принято как есть, без запрета удаления). Миграция создаёт пустую
> таблицу без бэкфилла — нулевое изменение поведения на проде в момент выката.
> Ошибки — `ChecklistError` (`WORK_LOCATION_NOT_FOUND`/`INVALID_LOCATION`/`INVALID_TEMPLATE`,
> `TEMPLATE_NOT_FOUND` переиспользуется).

> **Графики работы, авто-финиш по графику, переработки (`work_schedules`).** Организация получает часовой пояс (`organizations.timezone`, IANA, default `Europe/Moscow`, валидация `zoneinfo` → `400 INVALID_TIMEZONE`). **Графики** (`work_schedules`) — интервал внутри суток (`start_time`/`end_time`, `Time` без tz, локальное время организации); `end_time < start_time` — ночной график через полночь (`crosses_midnight`/`duration_minutes` — вычисляемые Python-свойства модели, не колонки). Назначение — калька модели чек-листов (роль/точка/личный override), с одним отличием (**R1**): график **без единой привязки действует на ВСЕХ** сотрудников (у чек-листов такой шаблон не выдаётся никому) — реализовано как отдельный канал `global_ids` в `_compute_effective_schedules` (`services/work_schedule.py`), наряду с `location_only_ids` (нет ролей, есть точки — на всех этой точки) и `role_ids`; фильтр по точке (`matches_location`, переиспользуется из `checklist_location.py`) применяется **после**, ко всем каналам одинаково, включая `personal_add`; приоритет — `remove` > назначение > `add`. **Расчёт планового окна** (**R2**, `compute_scheduled_window`) — по `started_at`, таймзоне организации и графику: три кандидата (вчера/сегодня/завтра по локальной дате начала), длительность прибавляется к наивному локальному времени ДО перевода в UTC — так через `ZoneInfo.astimezone(UTC)` корректно учитывается переход на летнее/зимнее время (реальная UTC-длительность ночного графика на переходе может быть на час короче/длиннее номинальной). **Старт org-смены** (**R3**, `_resolve_org_shift_schedule`) — после резолва точки: переданный `work_schedule_id` обязан быть в эффективном наборе (иначе `403 SCHEDULE_NOT_AVAILABLE`; отсутствует в org вовсе → `404 SCHEDULE_NOT_FOUND`); без явного выбора — 1 доступный подставляется автоматически, 0 или >1 требуют `require_schedule=false` (иначе `422 SCHEDULE_REQUIRED`) для старта без графика. Персональные смены (`organization_id is null`) графики **не применяют** вообще — все `scheduled_*` всегда `null`. **Авто-завершение** (**R4**) полностью переписано: раньше — Celery каждые 5 мин по `started_at + auto_finish_hours` (глобальному/органному) для ЛЮБЫХ смен, теперь — раз в **60 сек** по частичному индексу `ix_shifts_scheduled_end_at` (`WHERE status IN ('active','paused')`) строго для org-смен с `scheduled_end_at <= now()` и `auto_finish_by_schedule=true` (запись настроек отсутствует → считаем `true`); `finished_at = scheduled_end_at` (не момент срабатывания), `finish_reason=auto_schedule`, аудит `shift.auto_finish` с `work_schedule_id`/`schedule_name` в `summary`. **Персональные смены больше не авто-завершаются вообще** — глобальная настройка `default_auto_finish_hours` убрана из `core/config.py`. Inline safety-net в `start_shift` (`_auto_finish_stale_for_user`) переписан на ту же логику **и теперь тоже пишет аудит** (расхождение с фоновой задачей устранено). **Опоздание** (**R5**, `compute_late_seconds`) — не хранится, считается на лету: `max(0, started_at − scheduled_start_at − late_tolerance_minutes)`; `null` для смен без графика. **Переработка** (**R6**, `shift_overtime_requests`, `services/overtime.py`): сотрудник подаёт заявку на завершённой смене с графиком, где факт ≤ план (иначе `409 OVERTIME_NOT_APPLICABLE`), в течение `overtime_request_days` от `finished_at` (иначе `400 OVERTIME_PERIOD_EXPIRED`); максимум одна `pending`/`approved` заявка на смену (частичный уникальный индекс + повторная проверка на `IntegrityError` — закрывает гонку двух параллельных `POST`); после `rejected` можно подать заново; отозвать можно только `pending` (`DELETE`, 200 с конвертом `{data:null}` — не 204, чтобы не ломать контракт `{data,error}`); owner/admin согласует/отклоняет (`PATCH .../overtime-requests/{id}`), повторное рассмотрение → `409 OVERTIME_ALREADY_REVIEWED`; `ShiftResponse.overtime` показывает **последнюю** (по `created_at`) заявку смены независимо от статуса (в т.ч. `rejected` — с причиной отказа). `overtime_request_days` дополнительно **флэттится в `OrganizationResponse`** (`GET /organizations/{id}` и список организаций; `_org_to_response`, из `org.settings.overtime_request_days if org.settings else DEFAULT_OVERTIME_REQUEST_DAYS`, тот же паттерн, что и `geo_check_enabled`/`require_work_location`) — read-only, чтобы employee (без доступа к `/settings`) мог скрыть кнопку «Добавить переработку» после истечения срока, не дожидаясь `400 OVERTIME_PERIOD_EXPIRED`; редактируется по-прежнему только через `PATCH .../settings`. **Смена графика администратором** (**R7**, `change_shift_schedule`) — `scheduled_*` пересчитываются от неизменного `started_at`; `finished_at` завершённой смены не трогается никогда; новый график может быть архивным (проверка «доступен ли сотруднику» не выполняется — админ вправе назначить любой график org); `work_schedule_id=null` снимает график и отключает авто-завершение для смены; аудит `shift.schedule_change` с `old_schedule_id`/`new_schedule_id`/пересчитанным окном. **План/факт в зарплате** (**R8**, `services/payroll.py`) — additive: `overtime_seconds` (сумма `approved`), `paid_seconds = worked + overtime` (по нему `gross` для `hourly`; `per_shift` игнорирует переработку — план=факт, дельта 0), `planned_seconds`/`planned_amount_minor` (окно графика × ставку на `started_at`; без графика — план = факт), `delta_amount_minor = gross − planned`, `late_count`/`late_seconds_total`; округление плана — тем же правилом, что и факта (round-once на итог сотрудника в `granularity=none`, посуточно в детальном режиме — суммы бьются на всех уровнях). Новые эндпоинты — `work-schedules` CRUD+назначения, `my-schedules`/`members/{id}/schedules` (эффективный набор), `shifts/{id}/schedule` (R7), `shifts/{id}/overtime` (создание/отзыв), `overtime-requests` (реестр+рассмотрение); списки org-смен получили `only_late`/`work_schedule_id`/`has_overtime`. **Решения на неоднозначностях ТЗ:** (1) `ShiftResponse.overtime` — последняя заявка по `created_at`, а не только активная (иначе `rejected` без ре-подачи была бы невидима сотруднику); (2) `DELETE .../overtime` — 200 `{data:null}`, не буквальный 204 (проект нигде не возвращает пустое тело без конверта); (3) реестр `overtime-requests.user` отдаёт `user_name`+`display_name` раздельно (как везде в проекте, `member_display_name`), а не предварительно склеенную строку из примера ТЗ; (4) `PATCH /organizations/{id}` — `name` стал опциональным (exclude_unset), чтобы можно было патчить только `timezone`, не перечитывая текущее имя; обратная совместимость не нарушена (передача только `name` работает как раньше); (5) `WorkScheduleMemberOverride`/`ShiftFinishReason`/`OvertimeRequestStatus` — нативные PostgreSQL enum (как `OverrideType`/`ShiftStatus`), не `native_enum=False` — по инструкции ТЗ «как остальные enum проекта»; (6) `matches_location` и `_get_org_location` переиспользуются напрямую из `checklist_location.py` (не копия) — идентичная логика, риск расхождения исключён. Миграция `f2a3b4c5d6e7`.

> **CORS.** Подключён `CORSMiddleware` (`main.py`), источники — из `Settings.cors_origins` (env `CORS_ORIGINS`, CSV; пусто = выключено). Нужен браузерным клиентам: админке `smenka_admin` и веб-версии мобилки (`flutter build web`). `allow_credentials=False` — клиенты шлют JWT в заголовке `Authorization`, не в cookie (переход на httpOnly-cookie + CSRF — отдельная задача); `allow_methods`/`allow_headers=["*"]`.

> **Ставки и зарплата (payroll).** История ставок — источник истины: строка `organization_member_rates` действует с `effective_from`, прошлые записи не перезаписываются (новая ставка «с даты» = POST новой строки; PATCH — только исправление опечаток). Для каждой завершённой смены берётся ставка с максимальным `effective_from <= shift.started_at`; смены без ставки → `unpaid_seconds`/`unpaid_shifts_count`/`has_missing_rate` и не входят в `gross_amount_minor`. Деньги — целые копейки: накопление точным Decimal, half-up до копейки ровно один раз на итог сотрудника; `totals.gross` = сумма округлённых итогов. Расчёты не кэшируются. `MemberResponse.current_rate` (additive nullable) — действующая ставка `max(effective_from) <= now`, заполняется **только** для owner/admin/super_admin (для employee всегда null — приватность зарплат). Owner != member (ADR-001): в payroll-отчёте не фигурирует, `my-earnings` отвечает ему 403. Ошибки: `MEMBER_NOT_FOUND`/`RATE_NOT_FOUND` (404), `RATE_EFFECTIVE_FROM_TAKEN` (409, дубль по `UNIQUE (member_id, effective_from)` — закрывает и гонку), `INVALID_DATE_RANGE` (400, согласовано с date_filters).

> **Детальный отчёт + экспорт (`payroll_detailed_report`).** Аддитивное расширение `GET …/payroll` (новых таблиц/полей нет). Опц. query: `granularity` (`none｜day｜week｜month`, default `none`), `user_ids`/`location_ids` (повтор или CSV uuid; `location_ids=none` — смены без точки, чужие точки → `422 VALIDATION_ERROR`), `tz` (IANA, нарезка корзин; битая → `422`), `only_missing_rate` (bool). При `granularity != none` к каждому `items[]` добавляется `breakdown[]` (корзины с ненулевым числом смен, `bucket_start` ASC) и top-level эхо `granularity`/`tz`; при `none` ответ **байт-в-байт** прежний (полей нет). **Округление — посуточное** только в детальном режиме/экспорте: атом = локальный день в `tz` (half-up один раз/день), корзины week/month и итог сотрудника = суммы округлённых дневных значений (день→корзина→сотрудник→totals — всё «бьётся»); режим `none` сохраняет старое единичное округление на сотрудника (ADR-002, расхождение ≤ нескольких копеек). Корзина по `started_at` в `tz`; фильтр периода — по UTC до нарезки. `GET …/payroll/export` отдаёт `.xlsx` (`openpyxl`, не конверт `{data,error}`; ошибки до файла — конвертом): лист «Сводка» (агрегат+ИТОГО), «Детализация» (сотрудник×корзина), часы/деньги числами для суммирования в Excel; `format` — enum (`xlsx`), default `granularity=day`. Логика — `services/payroll.get_org_payroll`/`export_org_payroll`/`_build_breakdown`/`_build_payroll_xlsx`.

> **Штрафы (`fines`).** Owner/admin назначает сотруднику штраф фиксированной суммой (копейки, `amount_minor > 0`, всегда RUB) — из **шаблона организации** (`organization_penalty_templates`) или кастомный. Паттерн «шаблон → снимок» как у checklist: `reason`/`amount_minor`/`currency` копируются в `penalties` на момент создания; частичное переопределение тела допускается (`reason` из шаблона, `amount` свой и наоборот); правка/soft-delete шаблона выданные штрафы не меняет (`template_id` → SET NULL при физ. удалении, снимок сохраняется). `occurred_at`: при `shift_id` по умолчанию `= shift.started_at`, иначе обязателен (`422 VALIDATION_ERROR`); по нему штраф попадает в период зарплаты (`[date_from, date_to]`, `date_to` включ., UTC). Снятие штрафа и удаление шаблона — **soft-delete** (`is_deleted=true`, у штрафа фиксируются `deleted_by_user_id`/`deleted_at`; снимает любой owner/admin, не только автор); все читающие запросы фильтруют `is_deleted=false`, повторная операция над снятым → `404 PENALTY_NOT_FOUND`/`PENALTY_TEMPLATE_NOT_FOUND`. Валидации при назначении: member принадлежит org (иначе `404 MEMBER_NOT_FOUND`; **owner != member** ⇒ оштрафовать owner нельзя), shift принадлежит этому member+org и `is_deleted=false` (иначе `404 SHIFT_NOT_FOUND`), шаблон активен и в org (иначе `404 PENALTY_TEMPLATE_NOT_FOUND`). **Интеграция в payroll/my-earnings/export — additive**: новый query `include_penalties` (bool, default `true`) у `GET …/payroll` и `…/payroll/export`; в каждый `items[]` и `totals` добавлены `penalty_amount_minor`/`penalties_count`/`net_amount_minor` (`net = gross − penalty`, **может быть < 0**, не обрезается). Штраф учитывается независимо от ставки (даже при `gross=0`); сотрудник только со штрафами (без завершённых смен) **всё равно попадает в `items`** (union по member→user), иначе штраф «потерялся бы»; при `include_penalties=false` penalty-поля = 0, `net=gross`, union не делается. `my-earnings` учитывает свои штрафы всегда (флага нет). В `.xlsx` добавлены колонки «Штраф, ₽»/«К выплате, ₽» («Сводка» — по сотруднику, «Детализация» — период-уровень, Штраф=0/К выплате=Начислено по корзине). Логика — `services/penalty.py` (+ агрегаты `aggregate_penalties_by_user`/`aggregate_member_penalties` для payroll). `shifts.is_deleted` — отдельное требование заказчика (soft-delete смен), фильтруется во всех читающих запросах по сменам; пишущего эндпоинта удаления смены в этой фиче нет (заготовка).

> **Имя участника в организации (`member_display_name`).** Одна колонка `organization_members.display_name` (VARCHAR(100) NULL) — принадлежит связке user↔org, не пользователю: один и тот же человек в разных организациях может иметь разные `display_name`. `NULL` = не задано, везде используется настоящее `users.name`. Уникальность не требуется (два одинаковых `display_name` в одной org — не ошибка). Owner не является member (ADR-001) ⇒ у владельца `display_name` нет. **Запись/сброс** — `PATCH /organizations/{org_id}/members/{member_user_id}` (`{"display_name": "..." | null}`), owner/admin/super_admin (тот же `ensure_admin_or_owner`, что и у прочих управляющих операций над участниками); employee — `403 FORBIDDEN`, в т.ч. попытка переименовать самого себя (управленческий атрибут, не самообслуживание). Нормализация на сервере (`services/organization.normalize_display_name`): trim по краям, внутренние `\n`/`\r`/`\t` → пробел; пустая строка/только пробелы после нормализации → `NULL` (сброс); длина 1–100, иначе `400 INVALID_DISPLAY_NAME`; прочие управляющие символы — та же ошибка. Каждое изменение пишет аудит-запись `member.display_name_update` (`summary`: `user_id`/`old_display_name`/`new_display_name`). **Поле — additive и только для чтения в остальных эндпоинтах**: `display_name: string | null` добавлено РЯДОМ с существующим `user_name` (который продолжает быть настоящим именем и НЕ переименован/не удалён — обратная совместимость мобильных билдов) в `MemberResponse`, `ShiftResponse` (только орг-контекст, `ShiftIdentity.display_name`/`build_org_shift_identities`), `OrgChecklistInstanceResponse` (реестр чек-листов, outerjoin `OrganizationMember` в общем запросе), `PenaltyResponse` (список и деталь), `PayrollItemResponse` (обе проекции — агрегат и с `breakdown`, наследуется `PayrollDetailedItem`), `EmployeeStatsResponse` (`per_employee` статистики). Везде заполняется тем же batch-запросом/join, что уже достаёт имя/роль участника — без N+1. В персональных (не орг-) эндпоинтах поле не появляется.

> **Фильтры диапазона дат (date_filters).** Оба stats-эндпоинта принимают ровно один источник окна: пресет `period` (`day`/`week`/`month`, поведение не менялось) ЛИБО кастомный диапазон `date_from`/`date_to` (включительно по `Shift.started_at`, допускается открытый диапазон). Ошибки: `MISSING_STATS_RANGE` → `AMBIGUOUS_STATS_RANGE` → `INVALID_PERIOD` → `INVALID_DATE_RANGE` (этот порядок). В ответах stats добавлены `range_from`/`range_to` (фактически применённое окно), `period` стал nullable. Списочные эндпоинты смен получили валидацию `INVALID_DATE_RANGE`. Все границы нормализуются `services/shift.ensure_utc` (naive → UTC, aware → приведение к UTC) и в фильтрах, и в эхо-полях.

> **Усиление безопасности (security_hardening).** Три класса защит. **(1) Rate-limit** (slowapi, `core/rate_limit.py`) на `register`/`verify`/`resend-code`/`login` — ключ = IP клиента (`utils/request.get_client_ip`, первый из `X-Forwarded-For` за Caddy). Хранилище счётчиков — Redis (`rate_limit_storage_uri`||`redis_url`; в тестах `memory://`), пороги из ENV (`*_RATE_LIMIT`). Превышение → `429 RATE_LIMIT_EXCEEDED` в конверте `{data,error}` + `Retry-After`. Лимитер выключаем флагом `rate_limit_enabled`. **(2) Счётчик попыток кода**: `verification_codes.attempts` атомарно (`UPDATE attempts = attempts+1`, commit до отдачи ошибки) растёт на каждый неверный `verify`; при `>= max_code_attempts` (5) код «сожжён» → `429 TOO_MANY_CODE_ATTEMPTS`, нужен `resend-code`. **(3) Блокировка аккаунта** (`services/lockout.py`, Redis-ключ `login_fail:{email}` с TTL = окно): после `max_login_failures` (10) неудач — `423 ACCOUNT_LOCKED` на `account_lockout_minutes` (15) независимо от верности пароля; успех сбрасывает счётчик. Блокировка по email одинаково для существующего/несуществующего email (без enumeration-оракула); per-IP rate-limit ловит распределённый перебор. **Sentry** (`core/sentry.py`) включается только при `SENTRY_DSN` (иначе no-op; dev/CI/тесты без сети), `send_default_pii=False`, `max_request_body_size="never"`. Глобальный `@app.exception_handler(Exception)` ловит необработанные 500: лог через structlog (repr) + `capture_exception`, клиенту — тот же конверт `{data:null, error:{code:"ERROR"}}` (доменные ошибки и `RequestValidationError` идут своими хендлерами и в Sentry не шлются). **Аудит** пишется в той же транзакции, что и действие (см. `services/audit.py`, ниже).

> **Аудит действий (audit_logs).** Запись создаётся из endpoint-слоя ПОСЛЕ успешного сервисного вызова и ДО `session.commit()` — один commit, аудит не расходится с фактом. Покрытие: `org.update/delete/invite_rotate`, `member.join/remove/role_update`, `settings.update`, `location.create/update/delete`, `shift.finish` (actor = инициатор, IP из запроса), а также системные `shift.auto_finish`/`pause.auto_finish` из Celery (`record_sync`, `actor_user_id = null`). `summary` — ключевые поля без секретов (инвайт-код и токены не пишутся). Чтение — только `GET /organizations/{id}/audit-logs` (owner/admin, `created_at DESC`, фильтры `action`/`actor_user_id`/`date_from`/`date_to` с `date_to` включительно, пагинация limit≤200); `actor_name` подмешивается batch-запросом по `users` (или «Система» при null-акторе). Записи неизменяемы и не удаляются через API.

> **Вход через Google/Apple (oauth_login).** Верификация id-токена — JWKS + RS256 (`services/oauth_tokens.py`, поверх `python-jose`+`httpx`, без новых зависимостей): подпись по `kid` из заголовка, `iss`/`aud`/`exp`; `aud` сверяется с `client_id`, настроенным в `oauth_provider_settings` для присланной пары provider×client_type (не ENV — редактирует только super_admin через `PUT /admin/oauth-providers/...`). JWKS кэшируется in-memory с TTL 1ч; при неизвестном `kid` кэш **форсированно рефетчится один раз** перед отказом (иначе легитимные токены, подписанные только что ротированным ключом провайдера, отклонялись бы до истечения TTL). Единая логика поиска/создания пользователя (`services/oauth.py._link_or_register_user`, три ветки): (1) есть `oauth_identities` по `(provider, sub)` → вход; (2) иначе поиск `users` по `lower(email) = lower(token_email)` **из проверенного id-токена** — один совпавший → автолинк без доп. подтверждения (`is_verified` выставляется `true`), больше одного → `500 OAUTH_LINK_AMBIGUOUS` (легаси case-дубли), ноль → регистрация нового `User(password_hash=null, is_verified=true)`. Токены выдаются тем же механизмом, что и `/auth/login` (`create_access_token` + `_create_refresh_token_db`). Для Apple, у которой email/name приходят от провайдера только при самой первой авторизации, тело запроса `email`/`name` используется **только** как fallback-имя нового аккаунта — identity-матчинг (поиск/линковка) всегда идёт по `claims.email` из подписанного токена, никогда по значению из тела запроса (в первой версии реализации была уязвимость: непроверенный body-email использовался для автолинка, что давало захват чужого аккаунта при повторном Apple-входе без email в токене — поймано и исправлено на ревью до мерджа). `GET /auth/oauth/config` отдаёт фронтам `{google, apple}` (`client_id`+`enabled` либо `null`) — фронты обязаны скрывать кнопку при `null`/`enabled=false`; для Apple на Android читается конфигурация `(apple, web)` (нативного Apple SDK на Android нет). Ошибки — переиспользуют `AuthError` (`INVALID_OAUTH_TOKEN`/`OAUTH_EMAIL_NOT_VERIFIED`/`OAUTH_PROVIDER_UNAVAILABLE`/`OAUTH_LINK_AMBIGUOUS`/`OAUTH_PROVIDER_NOT_CONFIGURED`) и `AdminError` (`VALIDATION_ERROR` — недопустимая комбинация provider/client_type). **Вне scope:** отвязка провайдера, server-side revoke через Apple/Google token endpoints, эндпоинт-редирект для Apple-входа на Android (`apple/android-callback`) — обнаружен мобильным треком как отдельная потребность, не описан в ТЗ, требует отдельного решения аналитика.

> **Отправка кодов подтверждения по email (smtp_email).** Код верификации доставляется письмом через HTTP API Loops (`services/email.py`, транспорт `httpx.AsyncClient` — async, не блокирует event loop; ранее был SMTP/`aiosmtplib` — Яндекс закрыт как провайдер, антиспам резал исходящие). Флаг включения — непустой `LOOPS_API_KEY`: **выключен** (dev/CI/тесты) — письмо не шлётся, код как раньше возвращается в ответе `register`/`resend-code` и пишется в лог (`verification_code_generated`/`_resent`); **включён** (прод) — код уходит ТОЛЬКО письмом, в ответе `verification_code=null`, в логи код не пишется (`auth._log_code` опускает поле `code` при `email_enabled`). Поле `verification_code` в схемах остаётся **nullable** (обратная совместимость со старыми мобильными билдами — не удаляется). Запрос — `POST {LOOPS_API_URL}` с `Authorization: Bearer {LOOPS_API_KEY}`, телом `{transactionalId: LOOPS_TRANSACTIONAL_ID, email, dataVariables: {code, ttlMinutes}}` (оба dataVariables required в шаблоне Loops). Успех — только HTTP 200 и `{"success": true}`; всё остальное (не-2xx, `success:false`, таймаут/сетевая ошибка) — сбой отправки. Доставка вызывается из endpoint-слоя **после `session.commit()`**: пользователь/код уже сохранены, поэтому сбой Loops не теряет регистрацию — `email.deliver_verification_code` ловит `httpx.HTTPError` и неуспешный ответ, логирует (HTTP-статус + тело ответа Loops, без ключа и кода) и поднимает `AuthError("EMAIL_SEND_FAILED", 502)`; пользователь повторяет через `resend-code`. Env: `LOOPS_API_KEY`/`LOOPS_TRANSACTIONAL_ID`/`LOOPS_API_URL`/`LOOPS_TIMEOUT_SECONDS`.

> **Центр уведомлений (`notifications`).** Внутриапповая pull-модель без OS/web-push: клиент сам запрашивает ленту и счётчик, сервер ничего не push-ит. Одна таблица `notifications`, получатель — `User` (не `OrganizationMember`) — работает и для сотрудника в организации, и для персонального режима; `organization_id` — контекст события (`null` для платформенных/персональных). `type` — обычный `VARCHAR(48)` без CHECK-ограничения (не SQLAlchemy `Enum` на колонке) — новый тип уведомления будущей фичи не требует миграции схемы; `NotificationType` (`models/notification.py`) — только типобезопасность вызовов `create_notification` внутри бэка, не источник правды для БД. **Публичного эндпоинта создания нет** — уведомления создаёт исключительно сервисный слой (`create_notification`/`bulk_create_notifications`, без `commit` — транзакцией управляет вызывающий код), поэтому создание уведомления атомарно с бизнес-событием (например, назначением теста). `GET /notifications` — лента `created_at DESC`, опц. `unread=true`; `GET /notifications/unread-count` — для бейджа колокольчика; `POST /notifications/{id}/read` — идемпотентно (повторный вызов на уже прочитанном не двигает `read_at`, 200); `POST /notifications/read-all` — массово, только свои непрочитанные. Изоляция по `user_id` на каждом эндпоинте — чужое уведомление недоступно (`404 NOTIFICATION_NOT_FOUND`, существование не раскрывается). Единственный текущий производитель событий — `employee_tests` (`type=test_assigned` при назначении теста). Миграция `6686fd74797c`.

> **Тестирование сотрудников (`employee_tests`).** Паттерн «шаблон → снимок», как у чек-листов: админ/owner создаёт **шаблон** теста (вопросы `single_choice`/`multiple_choice` с вариантами и баллами) и **назначает** его сотрудникам; при старте попытки вопросы/варианты **снимаются в снапшот** (`test_attempt_questions`/`test_attempt_options`) — правка/архивация шаблона после старта попытки не искажает уже сданный результат. Инварианты шаблона (`services/employee_test.validate_template_payload`, единый код `422 TEST_TEMPLATE_INVALID`): ≥1 вопрос, у каждого ≥2 варианта, `single_choice` — ровно один верный, `multiple_choice` — минимум один, `points≥1`, `0≤pass_threshold_percent≤100`, `max_attempts≥1`; та же функция используется в `POST .../test-templates`, `PATCH .../test-templates/{id}` (если передан `questions`) и `POST .../test-templates/validate` (сухая проверка для кнопки «Проверить JSON» в админке, ничего не пишет). **Назначение** (`test_assignments`) — upsert по `UNIQUE(template_id, member_id)`: повторное назначение обновляет только `due_at`, не сбрасывает результаты; для КАЖДОГО нового назначения создаётся уведомление `test_assigned` через `services/notification.bulk_create_notifications` в той же транзакции (`session.flush()` до создания уведомлений — нужен `id` назначения в `payload`). **Прохождение** (`org_member`, сам про себя): старт попытки (`POST .../attempts`) гейтится тремя guard'ами — шаблон не архивный (`400 TEST_TEMPLATE_ARCHIVED`), не `passed=true` (`409 TEST_ALREADY_PASSED`), `attempts_used < max_attempts` (`409 TEST_ATTEMPTS_EXHAUSTED`); повторный вызов при уже открытой `in_progress` попытке возвращает её же (не плодит дубли), конкурентный старт дополнительно сериализован `SELECT ... FOR UPDATE` на строку назначения. **Грейдинг** (`submit_attempt`/`compute_awarded`) — all-or-nothing: полные баллы вопроса только если множество выбранных вариантов == множеству верных, иначе 0; `percent=round(score/max_score*100)`, `passed` сравнивается со **снимком** `pass_threshold_percent` попытки, не с живым значением шаблона (ADR-003 — колонка `test_attempts.pass_threshold_percent`, отсутствующая в исходной таблице `backend.md`, добавлена по явному текстовому требованию того же документа). После submit денормализуется `test_assignments`: `attempts_used+=1`, `best_percent=max(...)`, `passed` sticky (раз `true` — остаётся), `status` — `passed`/`failed` (если попытки исчерпаны)/`in_progress`. **Реестр для админки** (`GET .../test-templates/{id}/assignments`, `GET .../test-assignments`) отдаёт `TestAssignmentOut` с денормализованными `attempts_used`/`best_percent`/`passed`/`last_attempt_at` + **`last_attempt_id`** (additive nullable — id последней **сданной** попытки; `services/employee_test.get_latest_submitted_attempt_ids`, `DISTINCT ON` тем же паттерном, что `services/overtime.get_latest_overtime_for_shifts`): без этого поля реестр не мог открыть разбор попытки (`GET .../test-attempts/{id}`) — пробел обнаружен на ревью admin-трека (`docs/tasks/employee_tests/STATUS.md`) и закрыт контракт-фиксом аналитика до релиза бэка. Удаление назначения (`DELETE .../test-assignments/{id}`) запрещено при хотя бы одной сданной попытке (`409 TEST_ASSIGNMENT_HAS_ATTEMPTS`) — история сдач не теряется. Персональный режим (`organization_id=null`) тестов не касается — только организационные. Миграция `9632b96364fd` (зависит от `notifications` — назначение создаёт уведомление в той же транзакции).

> **Ручной учёт времени и начисления (`manual_time_entry`).** Два независимых инструмента для owner/admin организации, оба явно **исключают** сквозной доступ `super_admin` (`services/common.ensure_admin_or_owner` получил keyword-only `allow_super_admin: bool = True` — оба сервиса зовут его с `allow_super_admin=False`; единственная фича платформы с таким исключением, закреплено тестами на обеих сущностях). **A. Ручные смены** (`services/manual_shift.py`, роутер `api/v1/manual_shifts.py`, ошибки — переиспользуемый `ShiftError`): `POST .../shifts` создаёт смену сразу `finished`/`finish_reason=manual`, чек-листы не создаются; `PATCH .../shifts/{id}` — для `finished` можно менять всё, для `active`/`paused` — только `started_at`/`work_location_id`/`note` (передача `finished_at` завершает смену задним числом: открытая пауза закрывается этим `finished_at`, если начата раньше, иначе удаляется); удалённую смену (`is_deleted=true`) править нельзя (`404 SHIFT_NOT_FOUND`, сначала `restore`). `DELETE .../shifts/{id}` — soft-delete (переиспользует существующую `shifts.is_deleted`, заготовку `fines`); повторный `DELETE` уже удалённой → `404` (невидима). `POST .../shifts/{id}/restore` — **идемпотентно** для уже неудалённой смены (возвращает как есть, не ошибку); для реально удалённой — снимает флаги + проверяет пересечения (`409 SHIFT_OVERLAP`, если за время «удалённости» завели другую смену на этот интервал). **R2 (запрет пересечений)** — `_check_overlap`: `[started_at, finished_at]` не пересекается с интервалом любой другой **неудалённой** смены того же сотрудника **в этой же организации** (персональные и чужие-org смены не участвуют); активная/паузная смена-сосед считается открытой до `now`; касание границами — не пересечение (строгие неравенства `a1 < b2 and b1 < a2`). **R1 (валидация интервала)** — `started_at < finished_at` строго, длительность ≤ 48ч, не в будущем (допуск 60с). **R3 (паузы)** — `_validate_pauses` (работает и над Pydantic `ManualPauseInput`, и над ORM `Pause` — общий контракт `.started_at`/`.finished_at`): границы внутри интервала смены, паузы не пересекаются между собой (касание — можно), суммарно строго короче смены; полная замена списка при `pauses` в PATCH требует, чтобы у смены уже был известен `finished_at` (иначе `422 VALIDATION_ERROR` — нет верхней границы для проверки); если `pauses` не передан, но интервал сместился — существующие паузы ревалидируются против нового окна. Точка/график — `work_location_id` проверяется на принадлежность org (без фильтра архивности — у `WorkLocation` её нет); `work_schedule_id` — снимок планового окна вычисляется **той же** `compute_scheduled_window`, что и `PATCH .../shifts/{id}/schedule` (work_schedules) — логика не дублируется; ручное изменение `started_at` НЕ пересчитывает уже проставленное плановое окно (для этого — повторное применение графика через существующий эндпоинт). **B. Ручные начисления** (`services/adjustment.py`, роутер `api/v1/adjustments.py`, модель `PayrollAdjustment`, ошибки — новый `AdjustmentError`): симметрично `services/penalty.py`, но БЕЗ шаблонов и со знаковой суммой в обе стороны (`amount_minor != 0`, доплата `>0`/удержание `<0`); `occurred_at` — как у штрафов, по умолчанию `= shift.started_at` при переданном `shift_id`, иначе обязателен. `member_id` неизменен после создания (переназначение — только отменой и созданием новой записи). **Прозрачность для сотрудника (R7)** — единый паттерн в обоих сервисах: каждая операция A1–A4/B1–B4 в ТОЙ ЖЕ транзакции пишет `audit_logs` (новые `AuditAction`: `shift.manual_create`/`shift.manual_update`/`shift.delete`/`shift.restore`/`adjustment.create`/`adjustment.update`/`adjustment.delete`, новый `AuditResource.adjustment`) и уведомление сотруднику (новые `NotificationType.shift_manual_changed`/`payroll_adjustment_changed`, `payload` — `{shift_id/adjustment_id, action, ...}`), через `services/notification.create_notification` (без `commit` — коммитит роутер). `ShiftResponse` получил 7 additive-полей: `is_manual`(`created_by_user_id IS NOT NULL`)/`is_edited`(`edited_at IS NOT NULL`)/`manual_note`/`edited_at`/`is_deleted` читаются прямо со смены и видны **везде**, включая персональный `GET /shifts` (сотрудник видит пометку у себя); `edited_by_name`/`created_by_name` (имя админа) — **только орг-контекст**, батч без N+1 (`services/shift.build_manual_actor_names`, объединяет `created_by_user_id`/`edited_by_user_id` страницы в один запрос к `users`). **Payroll — additive**: `adjustment_amount_minor`/`adjustments_count` в `items[]`/`totals` (и `my-earnings`), `net = gross − penalty + adjustment` (обе поправки независимы, штраф по-прежнему не влияет на начисления и наоборот); новый query `include_adjustments` (default `true`, симметрично `include_penalties`); сотрудник только с начислением (без смен/штрафов) всё равно попадает в `items` (union по `user_id`, тот же приём, что у `penalties`); при `granularity != none` начисления НЕ раскладываются по `breakdown` (агрегат уровня сотрудника за период, как и штрафы); в `.xlsx` — колонка «Начисления/удержания, ₽» рядом со «Штраф, ₽». **A5 — новые фильтры списка** `GET /organizations/{id}/shifts`: `include_deleted` (bool, default false — показывать и soft-deleted, для ревизии/восстановления) и `only_manual` (bool, default false — `created_by_user_id IS NOT NULL OR edited_at IS NOT NULL`); оба — И с существующими фильтрами, учитываются в `total`/пагинации, поведение по умолчанию не меняется. **Побочный эффект в моделях:** три новых FK `shifts→users.id` (`created_by_user_id`/`edited_by_user_id`/`deleted_by_user_id`) сделали связь `Shift.user`/`User.shifts` неоднозначной для SQLAlchemy (4 пути FK между таблицами) — потребовался явный `foreign_keys=[user_id]`/`foreign_keys="Shift.user_id"` на обеих сторонах relationship (тот же паттерн, что `Organization.owner`/`owned_organizations` из `admin_created_accounts`). Миграция `c6d7e8f90013` (add columns + create table + 3 FK + 3 индекса + `CHECK amount_minor != 0`), обратима. **Сопутствующие фиксы в существующем коде, вскрытые ревью этой фичи** (soft-delete `shifts.is_deleted` впервые стал реально выставляться — раньше это была заготовка `fines`, ни один эндпоинт её не ставил): `services/overtime.review_overtime_request` не фильтровал `Shift.is_deleted` (в отличие от соседних функций файла) — рассмотрение заявки на переработку по удалённой смене проходило; `DELETE .../shifts/{id}` на `active`/`paused` смене принудительно завершает её (закрывает открытую паузу, `status=finished`) ДО soft-delete — иначе `finished_at` оставался `NULL` навсегда и `restore_shift` считал бы интервал открытым до текущего `now()` при каждой проверке пересечений; `PATCH .../shifts/{id}/schedule` (work_schedules, R7) — третий орг-контекстный вызов `_shift_to_response`, не обновлённый в первой версии диффа, теперь тоже получает `created_by_name`/`edited_by_name`.

## Фоновые задачи (Celery + Redis)

| Файл | Задача | Расписание |
|------|--------|------------|
| `tasks/shifts.py` | `auto_finish_stale_shifts` — org-смены с просроченным `scheduled_end_at` по графику (work_schedules, R4; персональные смены больше НЕ авто-завершаются), `finished_at=scheduled_end_at`, `finish_reason=auto_schedule` (+ аудит `shift.auto_finish`, actor=null) | Каждые 60 сек |
| `tasks/shifts.py` | `auto_finish_stale_pauses` — завершение просроченных пауз (+ аудит `pause.auto_finish`, actor=null) | Каждые 5 мин |
| `tasks/cleanup.py` | `cleanup_expired_tokens` — очистка протухших токенов/кодов | Ежедневно 03:00 UTC |
| `tasks/cleanup.py` | `cleanup_orphan_files` — удаление файлов-сирот (`is_attached=false`, старше `ORPHAN_FILE_TTL_HOURS`): объект в S3 + строка | Ежечасно |

**Инфраструктура:**
- Redis 7 — брокер Celery + хранилище rate-limit (slowapi) и счётчиков lockout
- Celery worker с встроенным Beat (один контейнер); включены task-события (`task_track_started`/`*_send_*_event`) для мониторинга (Flower в проде), `acks_late`, сигнал `task_failure` → structlog (+ Sentry через CeleryIntegration)
- Синхронные DB-сессии для задач (`sync_session_factory` в `database.py`)

## Внешние сервисы

- **Redis** — брокер Celery, хранилище rate-limit (slowapi) и счётчиков блокировки аккаунтов
- **Sentry** — error-tracking бэка (включается при `SENTRY_DSN`; провижининг — `DEPLOY_NOTES.md`)
